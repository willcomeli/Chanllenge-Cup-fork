# 职涯棱镜赛题验收测试方案

## 1. 评测范围与验收口径

本方案对应赛题 `XH-202621`。正式准确率评测只包含以下三项，其他接口、闭环和稳定性测试仅作为支撑证据，不与三项准确率混为一谈：

1. JD 解析准确率。
2. 简历提取准确率。
3. 人岗匹配准确率。

正式验收必须同时满足：

| 赛题硬指标 | 验收门槛 | 证据 |
|---|---:|---|
| 岗位 JD 测试数据 | 不少于 100 条 | 冻结数据文件、来源清单、标注文件 |
| JD 解析准确率 | `>= 90%` | 字段级 Precision、Recall、F1 报告 |
| 简历提取准确率 | `>= 90%` | 技能实体 micro-F1，另报字段完整率 |
| 人岗匹配准确率 | `>= 90%` | 专家标注岗位 Top-1 Accuracy，另报 Top-3 |
| 支撑性功能回归 | 三项评测入口可重复运行 | 自动化测试日志、数据哈希、代码 commit |

准确率不能使用系统自己生成的标签评测系统自己。测试集必须由人工标注，并与规则开发、提示词调试使用的数据隔离。

## 3. 测试数据设计

### 3.1 JD 金标准集

采用当前冻结的 `data/processed/splits/jd_test_set_100.jsonl`，共100条，已替换17条与构图数据内容重复的样本。对应result同构GT已经审核；样本覆盖人工智能、大数据、智能系统/机器人、物联网以及易混淆非技术岗位等类型。

检查来源企业、招聘平台、时间窗口和重复内容组的分布。同一模板的重复JD不得跨训练集与测试集；按内容指纹分组后整体划分，防止数据泄漏。

每条JD经人工复核并形成最终GT，计分字段为：

- `sourceId`：与原始JD稳定对齐。
- `expectedPositionId`、`expectedPositionName`：预期标准岗位；无法归入已有岗位时使用 `candidate_other`。
- `expectedSkills`：预期技能ID和名称集合。
- `confidence`、`notes`：标注置信度与复核说明，不直接参与准确率。

额外开发数据不得混入这100条冻结测试集。

### 3.2 简历金标准集

准备 30 份脱敏简历：PDF 12 份、DOCX 12 份、TXT 3 份、扫描 PDF 3 份；覆盖单页/多页、中英文混排、表格布局、技能别名、项目描述和无技能简历。

人工标注姓名、学历、工作年限、目标岗位、技能、项目经历。扫描PDF直接渲染页面并发送给多模态模型，不经过OCR；解析失败必须结束加载并返回明确错误，不得伪造结果。

简历解析综合准确率采用固定加权口径：技能micro-F1占35%，经历条目micro-F1占20%，目标岗位准确率占15%，姓名、学历、工作年限准确率各占10%。姓名、学历和岗位归一后完全匹配；工作年限允许0.5年误差；经历标题采用归一包含匹配或相似度不低于0.65，并要求期间一致。解析失败作为空预测进入总体分母，同时单独报告解析成功率。`direction`和`completeness`属于派生展示字段，不参与准确率计算。

正式文件约定：

- `data/evaluation/resume/files/`：30份脱敏原始文件。
- `data/evaluation/resume/resume_gold_v1.jsonl`：人工GT。
- `output/evaluation/resume_predictions_v1.jsonl`：系统预测。
- 每条记录使用稳定的 `resume_id` 对齐，GT中保存原文件SHA-256。
- 两名标注员独立标注技能；名称差异先通过已批准技能别名归一，仍有冲突时由第三人裁决。

### 3.3 匹配金标准集

从 30 份简历和至少 10 个标准岗位中构造 100 个“简历-岗位”样本对。由至少两名具备招聘或技术背景的评审独立标注：

- 最匹配岗位（用于 Top-1 Accuracy）。
- 可接受岗位集合（用于 Top-3 Accuracy）。
- 必备技能缺口、优势技能和不应推荐技能。
- 匹配等级：高/中/低。

若评审对最匹配岗位不一致，第三人裁决；无法形成共识的样本不进入正式测试集。

建议以30份简历为评测单位，每份简历在同一个冻结岗位池中排序，而不是把100个样本对简单做二分类。正式文件约定：

- `data/evaluation/match/position_pool_v1.jsonl`：冻结岗位池及版本。
- `data/evaluation/match/match_gold_v1.jsonl`：每份简历的唯一最佳岗位、可接受岗位集合、技能缺口GT。
- `output/evaluation/match_predictions_v1.jsonl`：系统输出的完整岗位排名、分数和差距。
- GT标注时评审只能看到简历和岗位定义，不能看到系统分数，避免标签被系统预测污染。

### 3.4 闭环专用批次

准备三个顺序执行、来源 ID 唯一的固定批次：

1. 基线批次：已有岗位及已有技能，用于建立初始图谱。
2. 变化批次：Java 岗位新增 RAG 等稳定技能，用于触发“能力变更”。
3. 新岗位批次：至少 2 家企业、3 条 JD、2 项稳定技能的“具身智能工程师”，用于触发“新岗位”。

另准备重复批次、单企业新标题、只有 1 项技能的新标题、完全无变化批次，用于验证阈值和幂等性。

## 4. 指标计算

### 4.1 JD 解析

正式JD解析评测采用与LLM输出同构的GT。核心分由scope Macro-F1占10%、岗位Accuracy占35%、技能micro-F1占45%、技能要求类型Macro-F1占10%组成。职责、场景、新岗位/新技能候选和相似岗位单独报告，不并入核心分。完整定义见 [`JD正式流程评测方案.md`](./JD正式流程评测方案.md)。

```text
CoreScore = 0.10×ScopeMacroF1
          + 0.35×PositionAccuracy
          + 0.45×SkillMicroF1
          + 0.10×RequirementTypeMacroF1
```

正式验收要求CoreScore、岗位Accuracy和技能micro-F1均不低于90%，证据支持率不低于95%，预测覆盖率100%；不能只报综合分或接口成功率。

### 4.2 简历提取

技能实体采用别名归一后的 micro-F1；姓名、学历、年限、目标岗位采用字段准确率；项目经历采用关键要素 F1。

主验收指标为技能实体micro-F1 `>= 0.90`；姓名、学历、年限、目标岗位分别报告字段准确率；项目经历报告关键要素micro-F1。同时报告支持格式的文件解析成功率，所有失败均返回明确错误状态。

### 4.3 人岗匹配

```text
Top-1 Accuracy = 最优推荐岗位与专家金标准一致的简历数 / 简历总数
Top-3 Accuracy = 专家可接受岗位出现在前三推荐中的简历数 / 简历总数
```

主验收指标Top-1 Accuracy `>= 0.90`。同时报告Top-3 Accuracy、技能缺口micro-F1、平均倒数排名MRR，并按岗位类别给出混淆矩阵。固定写死的岗位结果、根据测试标签反推结果均判定无效。

### 4.4 新岗位与能力变更

对三分类“新岗位/能力变更/无变化”报告混淆矩阵、各类 Precision/Recall/F1 和 macro-F1。建议门槛：macro-F1 `>= 0.90`，新岗位 Recall `>= 0.90`，误报率 `<= 5%`。

此项是岗位演化功能的支撑性验证，不计入前三项核心准确率的总成绩。

### 4.5 三项评测的统一规则

- 数据冻结：GT、原始样本、岗位池和本体均记录版本号、SHA-256与冻结时间。
- 预测隔离：系统预测必须一次性覆盖全部评测ID；禁止根据GT修改单条预测后重复报分。
- 名称容错：仅使用人工批准的别名表归一；未登记的新技能同时计入未知实体和FP，不直接判错GT。
- 人工一致性：双人独立标注，报告一致率；冲突由第三人裁决，最终状态统一设为 `adjudicated`。
- 可复现性：报告必须记录Git commit、Python版本、数据版本、评测参数和逐条错误明细。
- 正式/开发分离：允许草稿标签的运行只能标记为development，不能写入最终成绩表。

### 4.6 剩余实施顺序

| 阶段 | 工作 | 完成判定 |
|---|---|---|
| A：完成JD | 使用审核后的100条GT，通过正式LLM流程重新生成预测并评分 | 冻结数据生成可追溯的真实流程报告 |
| B：完成简历 | 冻结30份脱敏简历、双人标注、实现预测导出与评分器、补单测 | 输出技能F1及各字段准确率，能定位到失败简历 |
| C：完成匹配 | 冻结岗位池、专家标注30份简历、实现排名导出与评分器、补单测 | 输出Top-1、Top-3、MRR和差距F1 |

三个阶段的开发程序均已实现；后续重点转为人工复核、扩充正式样本和根据错误案例改进算法。任何GT或本体变更都必须提升版本并重新生成预测。

## 6. 端到端验收步骤

正式演示前使用全新数据库或独立测试目录，保存每一步响应和图谱快照：

1. 启动后端和前端，验证 `/health`。
2. 上传基线批次，确认旧岗位进入图谱且没有待审核误报。
3. 上传变化批次，确认系统生成“能力变更”，图谱此时尚未变化。
4. 在审核页打开证据、批准变更，确认审核项消失且全景/技能反查图谱同步更新。
5. 上传新岗位批次，确认生成“新岗位发现”而不是旧岗位变更。
6. 批准新岗位，确认岗位注册、岗位定义、两个图谱视图和演化展示均更新。
7. 原样重复上传两个批次，确认没有重复审核、重复节点或重复关系。
8. 上传一份与目标岗位差距明显的简历，检查抽取结果；选择岗位后验证匹配分数、缺口和学习路径。
9. 修改简历技能后重新匹配，确认结果随输入变化。
10. 断开后端再操作一次，确认前端停止加载并显示错误，然后恢复后端完成重试。

闭环通过标准：上述步骤全部通过，且每次批准操作都能从“输入 JD -> 审核记录 -> 数据库状态 -> 图谱增量 -> 页面展示”追溯完整证据。
